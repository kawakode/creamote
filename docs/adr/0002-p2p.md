# ADR 0002 : connexion directe entre pairs

- Statut : proposé (M3a)
- Date : 2026-11-16

## Contexte

Jusqu'à M2, toute session passe par le relay : latence en plus, bande passante à la charge du serveur, et sessions limitées sur le serveur officiel. La plupart des machines sont derrière un NAT, sans redirection de port.

## Décision

- **Hole punching UDP en QUIC**, sans STUN séparé : chaque pair utilise un unique endpoint quinn pour le rendezvous, la connexion directe et le relay. Le serveur de rendezvous joue le rôle de STUN (adresse observée).
- **Candidats** : adresse observée par le serveur, puis adresses LAN de la machine énumérées par l'OS (crate `if-addrs` : `getifaddrs` sur Unix, `GetAdaptersAddresses` sur Windows). Au plus 8, même famille d'adresses que l'endpoint.
- **Rôles fixes** (viewer client, host serveur) plutôt qu'une ouverture simultanée symétrique : pas de connexion en double à départager. Le host « perce » son NAT par des tentatives de connexion sortantes vers le viewer, qui les ignore.
- **Le viewer choisit le chemin** et le signale par le premier message (`DirectJoin` sur le direct, ou le premier message Noise sur le relay). Le relay est rejoint en parallèle : pas de délai supplémentaire quand le direct échoue, au prix d'une place relay occupée quelques secondes.
- **TLS non vérifié sur le direct** : le certificat du host est éphémère ; l'authentification mutuelle est celle de Noise, identique au relay. Le serveur ne peut donc pas usurper un pair en falsifiant des candidats.
- **`relay_only`** : un pair peut refuser de révéler son adresse ; le direct est alors désactivé pour la session.

## Alternatives

- ICE complet (`webrtc-ice`) : traverse aussi TURN/TCP, mais ajoute une pile WebRTC et des allers-retours de signalisation. À reconsidérer si les mesures montrent trop de replis relay.
- Paquets de « perçage » à TTL réduit pour éviter qu'un NAT trop strict ne crée un état pour le premier paquet entrant : demande un accès bas niveau au socket partagé par quinn. Non retenu tant que le banc de test ne le justifie pas.
- Synchronisation de l'envoi des `RelayGrant` selon le RTT de chaque pair : utile seulement pour ces mêmes NAT ; écartée pour l'instant.
